# 本地 PDF 英译中

这是一个在本机运行的英文 PDF → 中文翻译工作流。程序不调用收费翻译 API，也不会自动操控 Google Translate。

工作流程：

1. 从本地路径读取 PDF，可指定连续页码范围；
2. 默认自动识别：优先读取 PDF 文字层，仅对无文字层的图片页面使用 macOS Vision OCR；
3. 把相邻文字块保守地组装成语义段落，同时保存页、栏和多个视觉定位锚点；
4. 保护 URL、邮箱、DOI、引用、代码、公式标记和数值单位；
5. 自动拆分并生成 Google Translate 可用的 XLSX；
6. 用户手动在 Google Translate 网页翻译 XLSX；
7. 导回 XLSX 后自动检查并修复：缺失、空白或关键占位符损坏的段落保留原英文并列出说明；
8. 默认生成“原版面中文版”：保留原图、表格、装饰与页尺寸，只在英文位置修补背景并写入中文；
9. 也可生成“原文 + 原版面中文版”：原第 1 页、中文第 1 页、原第 2 页、中文第 2 页，依次交错。

## 译文来源约束

- 程序不内置任何书籍、页码、段落 ID 或样本 PDF 的固定译文；
- 每个任务的中文只来自该任务导回的 XLSX；
- XLSX 的任务标识、Row Key 和原文哈希用于阻止不同 PDF、不同任务之间串用译文；
- 程序不会内置或猜测译文。Google 返回内容缺失、为空或关键占位符无法安全恢复时，该段在原版面输出中保持原样，不擦除原英文，并在页面列出 Segment ID、原页码和原因；
- 只有翻译件属于其他任务、文件无法读取或 Row Key 重复等结构性问题才会阻止生成。

## 排版策略

页面默认选择 **原版面中文版**：

- 原 PDF 页面仍是输出页的底层，图片、表格、页码、装饰和页面尺寸不重建；
- OCR 保存每一行英文的坐标；
- 程序在英文笔画区域建立掩膜，用本地图像修复补回背景；
- 中文以矢量文字写回原段落框；多行段落沿原英文逐行轮廓流动，保留绕图、缩进和版面缺口，过长时逐步缩小字号；
- 跨栏或跨页的同一语义段落只进入 XLSX 一次，译文返回后再按原文比例分配到多个视觉锚点；
- 字号和行距会联合搜索，在不越过原框的前提下尽量保留较大的中文字号；
- 每段都被限制在原框内，无法放下时记入报告，不会静默溢出到相邻区域。

同页的英文背景会先统一修补，之后再一次性绘制所有中文，避免相邻文字区域的修补层遮住已经写入的汉字。

最终只提供两种输出：

- **原版面中文版（推荐）**：仅包含保持原页面结构的中文页。
- **原文 + 原版面中文版**：每个原文页后紧跟同一页的原版面中文版，不使用重排译文。

扫描页上的英文若压在照片、纹理或渐变上，擦除位置可能出现轻微修补痕迹。质量报告会列出溢出、原始框相交、缩小字号和复杂背景信息；正式处理整本书前应先抽查若干典型页面。

高密度索引或目录页会额外标记为 `needs_review`。即使其字号计算显示“零溢出”，扫描 OCR 仍可能漏掉紧密排列的小字，因此程序不会把这类页面自动判为通过。

## 轻量中间表示

项目借鉴 BabelDOC 的“语义内容与视觉定位分离”架构思想，但采用适合本项目的轻量独立实现，没有复制 BabelDOC 的 AGPLv3 代码，也不把 BabelDOC 作为运行依赖。

- `DocumentIR` 保存版本号、页面尺寸、旋转与页面框；
- 每个 `Segment` 代表一个可翻译的语义段落，并使用稳定的 `P0001-S000001` 形式作为 Paragraph ID / Row Key；
- 每个段落可以带一个或多个 `ParagraphAnchor`，分别记录页码、阅读顺序、栏号、原文字块和擦除坐标；
- 旧任务没有 IR 或仍使用纯数字 Row Key 时继续按旧结构读取，不会强制重新分析；
- 任务页的“检查段落结构”可以把锚点叠加到原 PDF 页面上，便于抽查多栏、跨页和表格边界。

## 安装与启动

推荐 Python 3.12，也支持 Python 3.11–3.13。

```bash
git clone https://github.com/xingdawang/pdf_translator.git
cd pdf_translator
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

macOS 可直接双击或运行：

```bash
./run_app.command
```

也可以：

```bash
source .venv/bin/activate
pdf-translator ui
```

Flask 页面默认打开 [http://127.0.0.1:5050](http://127.0.0.1:5050)。前端只使用服务端 HTML、原生 CSS 和少量 JavaScript，没有 Streamlit，也没有 Node 构建步骤。

## 页面使用

### 1. 导入并分析

可以点击“选择 PDF 文件”打开 macOS 原生文件选择器，也可以直接粘贴绝对路径。来自终端或 Finder 的路径即使带有单引号、双引号或反斜杠转义，也会在分析前自动整理。对于 300MB 以上文件，这种方式不会在浏览器和程序之间再复制一份文件。

“开始页”和“结束页”用于创建连续范围任务，例如填写 `1` 和 `20` 时，只分析、导出并生成原 PDF 的第 1–20 页；结束页留空表示处理到最后一页。任务中的段落继续显示原 PDF 页码。

选择文件或修改页码后，页面会快速抽取最多 5 个代表页面，显示 PDF 总页数、文件大小、当前范围、文字层情况和推荐识别模式。该检查不会提前 OCR 整本文件。

文字识别有两种模式：

- **自动识别（推荐）**：正常文字页直接读取文字层；只有文字不足且包含图片的页面才使用本地 macOS Vision OCR。
- **仅使用 PDF 文字层（最快）**：完全不运行 OCR，适合确定带文字层的电子出版物。

选择“仅使用 PDF 文字层”时，OCR 清晰度会自动禁用并明确标记为不生效。如果最终仍未检测到文字层，页面会保留原路径、页码和设置，并提供“改用自动识别并重新分析”按钮。

OCR 优先直接读取 PDF 中唯一的整页扫描图，并按照该图片在 PDF 页内的真实放置矩阵换算坐标；不能安全映射时才把当前页渲染为临时 PNG。每次 OCR 使用独立临时目录，识别后立即删除；辅助程序编译也带有跨线程、跨进程锁。复杂多栏、竖排标签和跨图片说明的阅读顺序仍需要人工抽查。

OCR 与原版面背景修补统一提供 170、200、240 DPI，默认 200 DPI。所有 DPI 选项及显示名称只在 `config.py` 定义。历史任务继续保留自身记录的 DPI；新任务默认使用 200 DPI。

首页不再展示页眉、页脚、纯页码和保护术语等高级翻译范围设置，以保持个人使用流程简洁；程序继续采用安全默认值。

任务页面只保留以下四步。

### 1. 导出翻译包

点击“生成 / 重新生成并下载 XLSX”，浏览器会立即下载结果。长文档会自动拆分：

```text
book_google_translate_001_of_003.xlsx
book_google_translate_002_of_003.xlsx
book_google_translate_003_of_003.xlsx
```

程序会先尝试生成单个 XLSX，并按实际文件大小检查；只有接近 Google Translate 文档翻译的 10 MB 上传限制时，才拆成尽可能少的多个翻译包。每包目标上限为 9.5 MB，留出少量安全余量。每一行对应一个完整语义段落，而不是任意切开的视觉文字块。

### 2. 打开 Google Translate

点击页面上的按钮打开 [Google Translate 文档翻译](https://translate.google.com/?sl=en&tl=zh-CN&op=docs)，逐个上传 XLSX 并下载结果。不要排序行、修改或重复 Row Key、合并单元格或把多个包拼在一起。

### 3. 导入翻译件

页面可一次选择多个翻译后的 XLSX。选中文件后会自动上传、导入、检查与修复，不需要再点击确认按钮。程序优先使用 Row Key 精确匹配；缺失行、空译文和无法安全恢复的关键内容会自动改为保留原英文，页面只提供一个默认折叠的清单供了解。原文与译文的数字差异默认放行，不进入待检查列表。

任务包不匹配、XLSX 无法读取或 Row Key 重复属于结构性错误，仍会要求重新选择正确的文件，防止把其他 PDF 的译文写入当前任务。

### 4. 生成结果

原版面背景修补提供三档：

- **轻量输出 · 170 DPI**：更省内存和临时空间；
- **标准输出 · 200 DPI（推荐）**：默认选择，兼顾背景修补清晰度和文件体积；
- **精细输出 · 240 DPI**：用于小字、细斜体或复杂纹理背景。

这里的 DPI 只控制英文擦除和背景修补，不会重新执行 OCR，也不会降低中文矢量文字的清晰度。程序会自动检测并使用当前机器的全部逻辑核心并行准备页面，同时限制在途页面数量，避免大文件把整本页面同时压入内存；每页的修补区域会合并为有限数量的局部无损透明图块，避免为分散的修改保存接近整页的大图，中文字体仍在主进程中按原顺序统一写入。PDF 内容流使用 Flate 压缩，写出前还会去除重复对象。

生成指纹包含原文件、页码、译文、占位符、字体、DPI 和渲染器版本。相同输入和设置重复生成时，会先验证已有 PDF 的文件大小、页数和页面尺寸，再直接复用；任何译文或生成设置变化都会自动失效并重新生成。

输出保存在：

```text
data/tasks/<TASK_ID>/outputs/
```

生成时使用的质量数据只保留在任务内部，页面不显示、也不提供报告或 JSON 下载入口。

任务页面的步骤导航位于顶部栏。点击可跳转到对应区块，滚动页面时当前区块会自动高亮；完成分析、导出、导入或确认后，页面会自动定位到下一项操作或本次检查反馈。

任务标题旁提供“清理缓存与旧文件”，会删除可重建缓存、临时文件和未被当前任务引用的旧输出；“删除任务”会先把任务目录移到本地 `data/trash/`，避免直接不可恢复地删除。

## 命令行

普通文本 PDF：

```bash
pdf-translator export "/path/to/input.pdf"
```

只处理第 1–20 页：

```bash
pdf-translator export "/path/to/input.pdf" --page-start 1 --page-end 20
```

扫描件（macOS）：

```bash
pdf-translator export "/path/to/input.pdf" --ocr vision --ocr-dpi 200
```

导入、检查和生成：

```bash
pdf-translator import TASK_ID translated_001.xlsx translated_002.xlsx
pdf-translator validate TASK_ID
pdf-translator generate TASK_ID
```

原版面替换使用更高的背景修补清晰度：

```bash
pdf-translator generate TASK_ID --layout-dpi 240
```

生成原文页与对应原版面中文版逐页交错的文件：

```bash
pdf-translator generate TASK_ID --output-mode source-layout
```

查看任务：

```bash
pdf-translator list
```

## 300MB 以上 PDF

- 文件哈希以 8MB 分块读取；
- PyMuPDF 逐页解析，不把整份 PDF 或全部图片加载进内存；
- 本地路径模式默认不复制原 PDF；
- OCR 和原版面背景修补都逐页处理，不把全书图像一次装入内存；
- 原版面背景修补按 CPU 逻辑核心并行处理，并把待处理队列限制在核心数的两倍；OpenCV 在每个页面工作单元中限制为单线程，避免嵌套并行抢占内存；
- 分析和生成在后台运行，页面显示逐页进度；
- 同一个分析或生成请求会自动去重，每个任务的写操作串行化；
- XLSX 自动分包；
- 生成前检查可用磁盘空间。

原版面中文版会保留任务所选范围内的原始页面，并给每页增加最多一个局部透明修补图层。处理整本时，最终文件可能接近或大于原 PDF，需要额外临时磁盘空间。300MB 以上文件建议先用页码范围抽取 3–5 个典型页面验证 OCR、擦除和字号，再处理全书。首次 OCR 会编译一个很小的 macOS Vision 辅助程序并缓存，后续重复使用。

## 中文字体

程序会依次查找：

- `PDF_TRANSLATOR_FONT` 指定的字体；
- 项目内 Noto Sans CJK；
- macOS STHeiti / Arial Unicode；
- Linux Noto Sans CJK；
- Windows 微软雅黑 / 黑体。

也可以通过环境变量或命令行指定：

```bash
pdf-translator generate TASK_ID --font "/path/to/NotoSansCJKsc-Regular.otf"
```

## 测试

```bash
pytest
```

测试覆盖段落 ID、占位符、XLSX 往返、导入校验、原版面替换、原文与中文版交错页序、PDF 重新打开和 Flask 页面。

GitHub Actions 会在 Python 3.11、3.12 和 3.13 上执行关键静态检查、编译检查和完整测试。

`scripts/generate_layout_stress_text.py` 只供开发时做排版回归测试。它根据当前任务每段原文的长度动态生成带有“排版校验”标记的非语义中文，并保留占位符与数字；它不是翻译器，也不会参与网页或正常 XLSX 工作流。

## 当前限制

- Vision OCR 目前只支持 macOS；
- OCR 识别质量取决于扫描清晰度，小字、装饰字体和化学式可能出现误识别；
- 复杂多栏和跨区域图注的阅读顺序需要人工抽查；
- 当前不支持表格语义识别与单元格重建；
- 原版面输出保留表格外观，但只替换 OCR 识别到的单元格文字，不重建表格语义；
- 照片、渐变或纹理上的英文使用局部图像修复，可能留下轻微模糊或色块；
- 中文比英文更长时会缩小字号；低于最小字号仍放不下的段落会在报告中标记为溢出；
- OCR 漏掉的英文不会被替换，因此正式输出仍需肉眼抽查；
- 复杂公式依赖双语版原文页核对；
- Google Translate 网页行为可能变化，翻译质量需要用户自行检查；
- 上传 XLSX 意味着其中的文本会发送给 Google，不适合敏感内容；
- 处理全部 300MB 扫描书可能耗时较长，且双语版需要较多磁盘空间。

```text
├── flask_app.py
├── templates/
├── static/

```

任务元数据与段落使用本地 SQLite 保存，避免一个持续膨胀的大 JSON 在每次修改时被完整重写；每个任务目录仍保留一个不含段落正文的小型 `task.json` 摘要。首次启动新版时，旧的完整 JSON 会自动迁移，并备份为 `task.legacy.json`。XLSX 仍是唯一的翻译交换格式，原 PDF、SQLite、JSON、XLSX、输出文件和质量报告全部留在本机。
